## Stable v1.4.0: Installed app: ChatGPT Accessibility

Default `install` reopens ChatGPT to check its Accessibility permission. If access is already valid, no authorization card is needed. If missing, the native guide opens automatically. Default `uninstall` checks the restored official app through the same guide.

![Real macOS installation authorization card, shown in Chinese](/incodex/images/accessibility-guide.png)

This real-window image shows the Chinese card; its language follows the local Codex setting. Choose **Allow**, drag the guide's ChatGPT app row into **System Settings → Privacy & Security → Accessibility**, enable it, and complete macOS authentication. The guide checks automatically and closes when access is verified. macOS 12 uses **System Preferences → Security & Privacy → Privacy → Accessibility**.

Back returns to the initial card. Skip or closing leaves permission setup unfinished without undoing installation. Run `incodex accessibility` to resume later. Only choosing Allow can reset ChatGPT's old Accessibility registration; same-bundle-ID copies share that registration. `--app` / `--clone` targets do not start this automatic handoff.

## Unreleased experiment: Screen Recording

**Unreleased experimental behavior — not included in stable v1.4.0:** The default `/Applications/ChatGPT.app` guide displays Accessibility and Screen Recording as separate rows. A granted row remains visible with its localized completion label and check mark (`Done ✓` in English). The CLI reports completion only after fresh probes confirm that both rows are granted.

The Screen Recording probe runs in the injected, normal ChatGPT Electron main process and calls the public `systemPreferences.getMediaAccessStatus('screen')` API. It reads permission status only. It does not request a screenshot or recording, reset `ScreenCapture`, or modify vendor CUA sidecars. This permission is separate from the terminal or launcher Accessibility permission and is not a prerequisite for `incodex open`.

Choosing the Screen Recording row action opens the macOS Screen Recording settings pane; it does not grant access. In System Settings, add or enable the current `/Applications/ChatGPT.app`. If macOS asks, quit and reopen ChatGPT normally. If an older ChatGPT entry does not work, remove it manually and add the current app.

When the official app is restored or the Runtime is missing, probe evidence remains `unknown`; do not label it granted or denied. Persistence across official-app updates still needs real-machine verification.

## Independent open: terminal or launcher

`incodex open` needs Accessibility for the **terminal or launcher that runs it**, to distinguish window close from minimize. This is separate from ChatGPT's permission. Enable the program requested by macOS and retry. The check occurs before session creation. `open --dry-run` does not request access.

## Keychain

After a macOS patch changes signing, a system dialog may ask the app to access **Codex Storage Key**. Verify the expected app and item before entering your **Mac login password**, then choose **Always Allow** if you want to retain access. Allow / Allow Once can prompt again. Deny mismatched requests. Do not enter that password into Incodex or Terminal.

## Remote-control device keys

Since v1.3.4: the normal installed macOS host can use a narrowly scoped classic login Keychain fallback for the official remote-control module's OS-protected, nonextractable P-256 key request after `-34018`. The original Security call runs first. Hardware-only requests, private windows and Windows are excluded; the official module and authorization APIs remain unchanged.

The fallback verifies that the private key is nonextractable and retains the system access-control list. It does **not** preserve Secure Enclave, Data Protection Keychain or ThisDeviceOnly protection semantics. A later signature change may require system Keychain access reauthorization. Existing inaccessible keys are not migrated, rotated or deleted automatically. Local create/read/sign/delete passed testing, and successful real remote-control authorization was confirmed with the candidate Runtime. Keychain authorization continuity after re-signing remains unverified.

**Unreleased macOS stable-signing experiment:** the compatibility adapter accepts only the existing ad-hoc host or a strictly verified host whose leaf certificate matches its private public-certificate registration. This shared identity check does not grant Accessibility, Storage Key or remote-control authorization. Each capability retains its own checks; no new identity store or permission service is added. A changed native adapter requires a full quit and reopen, not just a live Runtime UI update. Real authorization and continuity after the next official update remain separate acceptance gates.

## Other permissions and Appshot

Keychain approval and Computer Use access do not prove Accessibility access. Screen & System Audio Recording is a separate macOS permission. The unreleased experiment above displays Screen Recording as an independent row; changing it does not repair Accessibility access.

The modified macOS package cannot preserve a valid OpenAI signature. Official **Appshot / smart snapshot** photo and screenshot attachments stop working after install; this is not a camera-permission issue. [Uninstall](/en/commands/uninstall/) restores the official package and Appshot. The no-patch [open](/en/commands/open/) path does not change the app's signature.
