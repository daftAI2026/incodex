## Stable v1.5.0: Installed app permissions

Default `install` reopens ChatGPT to check Accessibility and Screen Recording. The native guide shows separate rows. If both permissions are granted, no authorization card is needed. If either is confirmed missing, the guide opens automatically. Default `uninstall` also checks the restored official app through this guide. Screen Recording remains `unknown` when the official app has no Incodex probe.

## Unreleased fix: restored-app Screen Recording receipt

This behavior is not part of the published v1.5.0 baseline. Real-app acceptance is pending.

After `uninstall` restores the unmodified official app, Incodex has no Screen Recording probe. A successful drop into the open System Settings window produces only a drop receipt. It does not prove that the Screen Recording row is selected, its switch is enabled, or the status is `granted`.

When Accessibility is already granted, the guide closes after the receipt and Screen Recording stays `unknown`. Check the current ChatGPT entry in System Settings. When Accessibility is not granted, keep using its permission actions; the screen receipt does not finish that row.

Normal installation and update flows use the injected host's real Screen Recording probe. Only a fresh probe reporting `granted` completes that permission; the manual receipt never substitutes for it.

![The Accessibility row of the macOS installation guide, shown in Chinese](/incodex/images/accessibility-guide.png)

This image shows the Accessibility row, not the full two-row guide. The guide language follows the local Codex setting. Choose **Allow**, drag the ChatGPT app row into **System Settings → Privacy & Security → Accessibility**, enable it, and complete macOS authentication. The guide checks automatically and closes when both permissions are verified. macOS 12 uses **System Preferences → Security & Privacy → Privacy → Accessibility**.

Back returns to the initial card. Skip or closing leaves permission setup unfinished without undoing installation. Resume with `incodex perm` or `inc perm`; `accessibility` and `permissions` are not aliases. See the [perm command page](/en/commands/perm/). An explicit Accessibility Allow can reset ChatGPT's old Accessibility registration only after a locked fresh check confirms access is still missing. Same-bundle-ID copies share that registration. `--app` / `--clone` targets do not start the default automatic handoff.

## Screen Recording and `perm`

Run `incodex perm` or `inc perm` to check both permissions and continue setup. The command has no `accessibility` or `permissions` alias. The default `/Applications/ChatGPT.app` guide displays Accessibility and Screen Recording as separate rows. A granted row remains visible with its localized completion label and check mark (`Done ✓` in English). The CLI reports completion only after fresh probes confirm that both rows are granted.

The guide preserves the existing names and icons on macOS 26 and earlier. On macOS 27 and later, it reads permission names and icons from the running system: the English names are “Device Control and Data Access” and “Screen & System Audio Recording”; the former uses a blue folder-and-gear icon. Names follow the guide language. Languages absent from the system use Apple's English name; missing resources retain bundled fallbacks. This changes presentation only, not permission checks, Settings links or authorization actions. Real-window acceptance on macOS 26 and authorization continuity across signing changes remain unverified.

The Screen Recording probe runs in the injected, normal ChatGPT Electron main process and calls the public `systemPreferences.getMediaAccessStatus('screen')` API. It reads permission status only. The probe itself does not request a screenshot or recording, reset `ScreenCapture`, or modify vendor CUA sidecars. This permission is separate from the terminal or launcher Accessibility permission and is not a prerequisite for `incodex open`.

On an explicit Screen Recording Allow, the guide rechecks the target under its existing App lock. Only a fresh result that still confirms missing access authorizes one reset of ChatGPT's old `ScreenCapture` registration per guide, followed by Settings. This retires a stale signing requirement; it does not grant access. A granted or unknown result never authorizes this reset. Retry only reopens Settings. In System Settings, add or enable the current `/Applications/ChatGPT.app`. If macOS asks, quit and reopen ChatGPT normally. Completion still requires fresh grants from the current host.

When the official app is restored or the Runtime is missing, probe evidence remains `unknown`; do not label it granted or denied. Permission readings belong to the observed host generation and are checked again after an update.

## Independent open: terminal or launcher

`incodex open` needs Accessibility for the **terminal or launcher that runs it**, to distinguish window close from minimize. This is separate from ChatGPT's permission. Enable the program requested by macOS and retry. The check occurs before session creation. `open --dry-run` does not request access.

## Keychain

After a macOS patch changes signing, a system dialog may ask the app to access **Codex Storage Key**. Verify the expected app and item before entering your **Mac login password**, then choose **Always Allow** if you want to retain access. Allow / Allow Once can prompt again. Deny mismatched requests. Do not enter that password into Incodex or Terminal.

## Remote-control device keys

Since v1.3.4: the normal installed macOS host can use a narrowly scoped classic login Keychain fallback for the official remote-control module's OS-protected, nonextractable P-256 key request after `-34018`. The original Security call runs first. Hardware-only requests, private windows and Windows are excluded; the official module and authorization APIs remain unchanged.

The fallback verifies that the private key is nonextractable and retains the system access-control list. It does **not** preserve Secure Enclave, Data Protection Keychain or ThisDeviceOnly protection semantics. A later signature change may require system Keychain access reauthorization. Existing inaccessible keys are not migrated, rotated or deleted automatically. Local create/read/sign/delete passed testing, and successful real remote-control authorization was confirmed with the candidate Runtime. Keychain authorization continuity after re-signing remains unverified.

The stable local signing identity allows registered default installs to attempt recovery after an official Sparkle update. The compatibility adapter accepts only the existing ad-hoc host or a strictly verified host whose leaf certificate matches its private public-certificate registration. This shared identity check does not grant Accessibility, Storage Key or remote-control authorization. Each capability retains its own checks; no new identity store or permission service is added. A changed native adapter requires a full quit and reopen, not just a live Runtime UI update. Permission continuity across signing changes remains unverified.

## Other permissions and Appshot

Keychain approval and Computer Use access do not prove Accessibility access. Screen & System Audio Recording is a separate macOS permission. The guide displays Screen Recording as an independent row; changing it does not repair Accessibility access.

The modified macOS package cannot preserve a valid OpenAI signature. Official **Appshot / smart snapshot** photo and screenshot attachments stop working after install; this is not a camera-permission issue. [Uninstall](/en/commands/uninstall/) restores the official package and Appshot. The no-patch [open](/en/commands/open/) path does not change the app's signature.
