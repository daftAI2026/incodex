## Start with diagnostics

```bash
incodex --version
incodex status --json
incodex doctor --json
```

These commands do not repair or request permission. On macOS, `doctor --deep` adds nested-signing, entitlement, and Gatekeeper evidence. Ad-hoc signing is expected after install; Gatekeeper output alone is not proof of a failed install.

## macOS refuses to launch after install

Codex build 26.1007.21159 includes a restricted communication-notification entitlement that an ad-hoc signature cannot retain. Affected earlier installations can pass signature verification but fail to launch with Code 163. Run `inc update`; if already affected, run `incodex uninstall` to restore the official app, then `incodex install`. Updating the CLI and Runtime alone does not re-sign the app. This does not diagnose a dots HTTP 409.

## macOS remote-control key creation fails before the browser opens

This recovery applies to the existing classic login Keychain fallback for local key creation when the official remote-control module reports missing entitlement (`-34018`). Run `inc update`, fully quit and reopen Codex, then retry authorization. Updating Runtime does not re-sign Codex. After a Sparkle update, the registered default install attempts recovery; if integration remains missing, run `incodex install` against the current app. `--app` and `--clone` use their original install flow. These startup instructions describe key creation, not the separate device-key signing path below.

This targets local device-key creation, not dots HTTP 409 or every remote-control failure. The official web and cloud authorization flow remains in place. Local create/read/sign/delete tests cover those operations only. They do not prove remote enrollment or authorization continuity after a real official Codex update. Existing inaccessible keys are not automatically migrated or deleted. See [permissions](/en/permissions/) for the Keychain protection boundary.

**Stable local signing identity:** the compatibility adapter accepts the existing ad-hoc host or a strictly verified host whose leaf certificate matches the private public-certificate registration. This identity check does not grant Accessibility, Storage Key or remote-control access. To migrate an existing ad-hoc-signed default macOS install, explicitly run `incodex uninstall` then `incodex install` once; the new identity may need an initial grant. Do not reset permissions or regenerate device IDs to repair an identity check. Permission continuity across signing changes remains unverified.

## macOS remote-control device-key signing waits for system approval

The installed macOS Runtime routes only the official module's existing OS-protected, nonextractable P-256 device-key public/sign operations through `incodex-device-key-helper`. Other keys and APIs remain on the official path. This does not create or migrate a key. Do not apply the key-creation recovery steps above to this signing path.

When macOS shows an authorization dialog, verify that it names `incodex-device-key-helper` and that the request occurs during Remote Control. Enter your **Mac login password only in the system dialog**. **Always Allow** applies only to the current key/helper pair; a different key or changed helper identity may need approval again. Authorization continuity after a real official Codex update has not been tested.

Public-key requests, helper verification and complete request transfer retain the five-minute machine deadline. After the helper receives a complete signing request, it waits for the system/helper response, helper exit or host shutdown instead of ending the approval wait at the deadline. Denial and cancellation still fail. The helper does not retry or switch to another signer.

A successful local signature does not prove remote enrollment, connection or server acceptance. A remote-environment offline message does not identify a local Keychain failure. Use the official remote-control state to determine whether enrollment or connection completed.

## No hat after an update

Check whether integration is installed and which Runtime is selected. Run `inc update` to update the CLI and publish its bundled Runtime. Compatible UI/action changes apply live; other Runtime changes require reopening. The registered default macOS install attempts recovery after a Sparkle update; if the entry remains missing, run `incodex install` against the current app. Runtime publication alone does not install the app entry.

## No installation authorization card

The setup guide checks Accessibility and Screen Recording separately. Use [`incodex perm`](/en/commands/perm/) or `inc perm` to resume; `accessibility` and `permissions` are not aliases. The guide opens only for confirmed missing access; `unknown` stays pending. A reset requires explicit Allow and a locked fresh check that confirms access is still missing. Do not reset unrelated permissions.

## Open fails or takes unusually long

Read the terminal result and check the official app's own startup and network availability. On macOS, verify the launching terminal's Accessibility. On Windows, check the current user's Store package with doctor. Retrying does not justify copying a package, deleting official configuration, or bypassing ownership checks.

## Unexpected language or onboarding

The private window should inherit the normal Codex language and configuration. Compare the normal app first. Report repeated failures with CLI version, official app version, launch path, and sanitized diagnostics. Do not publish auth.json, config secrets, chat databases, or private logs. A fresh survey is not accepted as the intended private-window behavior.

## Windows install refuses while running

Finish active tasks, quit using Ctrl+Q or tray Quit, then retry. Incodex does not force the official app to exit. Experimental Store-update observation is not a guarantee of the first post-update cold launch.

## Session leftovers or interrupted installation

Inspect doctor. Never delete the normal `~/.codex` databases. For interrupted macOS mutations, use the exact transaction's [recover](/en/commands/recover/). Uncertain state is retained rather than blindly destroyed.

## Getting help

[Open a project issue](https://github.com/daftAI2026/incodex/issues) with sanitized facts. For vulnerabilities, follow [SECURITY.md](https://github.com/daftAI2026/incodex/blob/main/SECURITY.md), not a public issue.
