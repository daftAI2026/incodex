> **Unreleased experiment — not part of stable Incodex 1.5.4.** The installed and unmodified-app launch paths and private-window lifecycle have been exercised on macOS. Page reload and same-process hot update remain acceptance gates.

`inc` and `incodex` are interchangeable for this command and its flags.

```bash
incodex launch [--dry-run] [--app <path>]
```

`launch` starts normal Codex on macOS without copying, patching, or re-signing the app. It selects the existing integration automatically:

- **Already installed with Incodex:** reuse the recorded install, its Loader, IPC, Runtime, menus, and permission flow. A normal LaunchServices request opens or activates that app. No additional CDP controller starts and no Runtime is published. You do not need to uninstall first.
- **Uninstalled official app:** start the unmodified app with loopback CDP. Reuse the shared hat control and action factory, forwarding private-window requests to the existing Rust `open` lifecycle.

Windows keeps the existing `install` integration and official icon. This macOS alternative does not add a Windows launcher bundle or a second injection path.

For the installed branch, an already running app supports normal activation. For the CDP branch, another `launch` requests activation of a window already owned by this launcher; quit an app started by another route normally first. The command does not close Codex.

Before starting Codex, the command creates `~/Applications/Incodex Launcher.app`. A conflicting external bundle is rejected before the official app starts. This thin shell invokes the same CLI and preserves `HOME`. It does not copy configuration or sessions. Installed CLI links remain channel-stable rather than pinning a Homebrew Cellar version. The Finder entry exits; only the CDP branch retains an App-scoped CLI, so keep that terminal command running. An accepted launch request is not proof of visible UI readiness. Use the terminal form for diagnostics; the Finder entry has no separate error UI. Dedicated colored artwork is not yet supplied or accepted.

## Flags

| Flag | Meaning |
| --- | --- |
| `--dry-run` | Print the target app, executable, and launcher path. Do not open a window or write files. |
| `--app <path>` | Select an official Codex `.app`; the default is `/Applications/ChatGPT.app`. |

## Runtime updates

An installed app keeps its existing Runtime update path. The contracts below apply only to the uninstalled CDP branch.

While `launch` is running, compatible updates to the injector and shared action factory use the existing `UiUpdate` transaction. The renderer and action controller must both acknowledge the new generation. A missing or superseded acknowledgement rolls the change back. A native-open request verifies that its CLI contains the selected Runtime; a stale CLI fails without publishing older assets. Changes to native or other non-hot-swappable Runtime assets require a restart; this path does not provide full feature parity with `install`.

The uninstalled CDP branch does not supply existing Dock/status menus or installed permission probes. `incodex install` remains the existing app-integration path. Its private windows use the unreleased WindowServer close observer and do not require CLI or launcher Accessibility access. This does not grant or transfer the official app’s permissions.

While its private child is alive, repeated hat clicks reuse that owner and request foreground activation. Success requires the private guardian’s actual page and system-activation acknowledgement, not merely a successful pipe write. A missing control capability or failed activation fails only that request and retains the private window. These focus and reactivation paths still require real-app acceptance. If no normal page remains, reactivation fails rather than silently launching another app.

## Examples

```bash
incodex launch --dry-run
incodex launch
incodex launch --app "/Applications/ChatGPT.app"
```

Use `incodex launch --help` for your installed version. The new entry point remains unreleased until page reload and same-process hot-update acceptance pass. Automated tests do not replace those real-app checks.
