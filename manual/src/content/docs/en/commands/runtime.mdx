`inc` and `incodex` are interchangeable for this command and all its flags.

```bash
incodex runtime
```

Writes validated Incodex assets under `~/.incodex/runtime/`; never patches or re-signs the official app. Fully quit and reopen Codex to load the selected generation. It does not add app integration or upgrade an old installed loader. Normally inc update performs this stage automatically.

## Unreleased: compatible macOS Runtime updates

Once a normal macOS Codex process has started with the new Runtime, publishing a release that changes only the UI injector or the supported main action module automatically updates its existing supported windows. All windows must acknowledge the candidate before it becomes current; failed activation attempts roll back to the previous UI. Publication does not reload the official page or restart Codex.

The first upgrade from an older Runtime still needs a full quit and reopen. The action module routes opening incognito windows and configuring menus; stable authorization, launch/session ownership and native handles remain in the existing controller. New requests use the committed action generation, while pending requests finish with the generation they captured. Changes to other main-process code, preload, native components or other external assets still require reopening. A changed installed loader requires `incodex install`; reopening alone does not replace the ASAR loader. An already-open incognito window retains its original privacy implementation until it closes normally. Windows automatic reactivation is a separate acceptance milestone. The published v1.3.4 behavior above remains the stable baseline.

The unreleased macOS controller records separate verified publication, startup controller, committed main-action and acknowledged per-window generations in its existing launch log. Records correlate with the host PID and process start identity. A missing renderer acknowledgment or failed verification remains explicit; disk publication or CLI status alone does not prove activation.

## Unreleased: Windows installed Runtime updates

The Windows candidate applies compatible UI-injector and shared business-action updates to the running installed window, using its existing helper. It requires a real renderer acknowledgement and a fresh selection check before committing the action generation, then confirms the commit. Failure attempts rollback of both. New requests use the committed action generation; pending requests finish with the generation they captured. The installed bridge continues to expose only opening an incognito window. It does not restart Codex or refresh its page. This installed-App path has passed real-App hot-update acceptance. Automatic recovery across a real Windows Store update remains experimental.

An older helper does not contain this controller. Enabling it for the first time requires an explicit `incodex install` after Codex has exited normally. That initial setup is separate from testing hot updates: the A → B → A test must keep the same helper, App process and page running. Other Runtime asset changes require reopening; changing the native helper requires explicit installation. An already-open incognito window keeps its original privacy implementation until normal close.

For the first upgrade to v1.4.0, run `inc update` first to update the installed CLI and publish its bundled Runtime. Then finish active work, exit Codex normally, and run `incodex install` once to refresh the macOS loader catalog or Windows helper.

## Flags

| Flag | Meaning |
| --- | --- |
| `--dry-run` | Preview publication (documented by Windows help; accepted by the native macOS CLI too). |

## Examples

```bash
incodex runtime --dry-run
incodex runtime
```
